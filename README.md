# Система учета транспортных средств организации

## Назначение

Система учета транспортных средств организации - учебный программный проект для учета и управления транспортными средствами организации. Проект разрабатывается по дисциплине «Основы разработки защищенного программного обеспечения и компьютерных сетей».

## Индивидуальный вариант

Вариант 19 - система учета транспортных средств организации.

## Основные роли пользователей

- Водитель - просматривает закрепленные транспортные средства и передает сведения о поездках.
- Диспетчер - ведет учет транспортных средств, назначает их водителям и контролирует состояние.
- Администратор - управляет учетными записями, ролями, настройками системы и событиями безопасности.

## Используемые технологии

- Python 3.11 or newer;
- Git;
- python-dotenv;
- pytest.

## Структура проекта

- `app/` - исходный код приложения;
- `tests/` - автоматические тесты;
- `docs/` - документация проекта;
- `.env.example` - безопасный шаблон конфигурации;
- `.gitignore` - правила исключения конфиденциальных и служебных файлов;
- `requirements.txt` - зафиксированные зависимости проекта.

## Запуск проекта

1. Создать и активировать виртуальное окружение: `python3 -m venv .venv` и `source .venv/bin/activate`.
2. Установить зависимости: `python -m pip install -r requirements.txt`.
3. Скопировать `.env.example` в `.env` и заменить `APP_SECRET_KEY` случайным значением длиной не менее 32 символов.
4. Выполнить запуск: `python -m app.main`.

## Тестирование

Запустить автоматические проверки: `python -m pytest -q`.

Проверка входного контракта не заменяет аутентификацию, авторизацию, HTML-экранирование при отображении, параметризацию запросов или ограничение частоты сетевых обращений.

Подробный вывод тестов: `python -m pytest -v`.

## Версия v0.6 — защищённая работа с SQLite и вложениями

`app/repositories/requests.py` выполняет операции с SQLite через параметры `?`; режим сортировки выбирается из фиксированного списка. `app/storage/files.py` сохраняет файлы под случайными внутренними идентификаторами, ограничивает размер 1 МиБ и проверяет минимальные признаки форматов. Для `vehicle_photo` поддерживается ограниченная проверка сигнатуры PNG. `RequestService` объединяет сохранение файла и записи; при ошибке БД пытается удалить уже сохранённый файл.

Каталог вложений должен быть доступен на запись только учётной записи приложения. Открытие файлов использует `O_NOFOLLOW` и файловый дескриптор каталога; на ОС без нужных возможностей операция завершается отказом. Сигнатура не является полным анализом безопасности PDF или изображения. Демонстрация использует временный каталог и удаляет его при завершении: `python demo_v06.py`. Тесты: `python -m pytest -q` либо `python -m unittest discover -s tests -p "test_v06.py" -v`.

Компоненты ЛР6 являются учебным локальным прототипом. В проекте всё ещё нет сетевого API, аутентификации/авторизации для заявок, антивирусного анализа и атомарной транзакции между файловой системой и SQLite. Результаты и ограничения описаны в `docs/lab6_security.md`.

## Версия v0.7 — безопасная аутентификация

Добавлен `AuthService` (`app/auth.py`) с локальным SQLite-хранилищем, парольной политикой NFC, PBKDF2-HMAC-SHA-256 и 600 000 итерациями по умолчанию, временной блокировкой после пяти ошибок, проверкой и отзывом серверных сеансов, а также одноразовым восстановлением по резервному коду. Компонент возвращает подтверждённый сервером `user_id`; интеграция с прикладными ролями и защищёнными операциями автопарка ещё не выполнена. Проект остаётся локальным прототипом, а не веб-сервисом.

Запуск безопасной демонстрации на искусственных данных: `python demo_v07.py --mode all`. Доступны независимые режимы `register-login`, `salts`, `lockout`, `variant-19`, `sessions`, `recovery` и `production-kdf`. Только обычный режим использует `600000` итераций; тесты сокращают стоимость через внедряемый параметр. Демонстрация работает во временной папке и не выводит значения секретов. Тесты: `python -m pytest -q`.

Схема и остаточные риски: `docs/authentication.md`, `docs/auth_registration_login.mmd`, `docs/auth_session.mmd`, `docs/auth_recovery.mmd`. Материалы ЛР7 — `reports/lab7/`. Скриншоты должны быть получены в обычном терминале согласно локальным шагам `LAB7_STEPS.md`; до этого отчёт является предварительным.

## Состояние версии v0.2

Лабораторная №2 формирует проектные требования безопасности, реестр активов, предварительную матрицу доступа и сценарии приемки. Документы описывают планируемую систему учета автопарка и не означают, что соответствующие функции уже реализованы.

Фактически приложение пока загружает и проверяет конфигурацию (`APP_NAME`, `APP_ENV`, `APP_SECRET_KEY`) и печатает стартовое сообщение без вывода секрета. В коде отсутствуют учет транспортных средств и поездок, аутентификация, авторизация, база данных, журнал аудита и сетевой интерфейс.

Подробности: `docs/project_description.md`, `docs/assets.md`, `docs/access_matrix.md`, `docs/security_requirements.md`, `docs/acceptance_scenarios.md`.

## Фактические меры конфигурации

- конфигурация загружается из переменных окружения и `.env`;
- проверяются непустое имя приложения, допустимое значение среды и минимальная длина `APP_SECRET_KEY`;
- стартовое сообщение не включает секрет;
- `.env` исключен из Git, для настройки есть шаблон `.env.example`.

Эти проверки не являются аутентификацией пользователей и не обеспечивают разграничение доступа.
