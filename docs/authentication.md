# Подсистема аутентификации v0.7

## Назначение и границы

`app/auth.py` реализует учебную локальную подсистему аутентификации. Она подтверждает учётную запись паролем и возвращает только серверный `user_id` при проверке действующего сеанса. Слой не определяет роль и не связывает её с пользовательским вводом. Существующий `Principal` из RBAC должен получать доверенную роль из отдельного серверного отображения; такой интеграции в v0.7 нет.

Хранилище — SQLite в локальном файле. Это не распределённая система идентификации и не веб-сервис. Каждое соединение включает `PRAGMA foreign_keys=ON`; запросы используют связанные параметры. `BEGIN IMMEDIATE` применяется для сериализации изменений счётчика входов, создания сеанса и одноразового применения recovery-кода. Он уменьшает гонки между писателями SQLite, но удерживает блокировку на время транзакции; это приемлемо для небольшой локальной лабораторной БД, не является масштабируемой очередью или распределённой блокировкой.

## Данные

`users`: числовой `id`, нормализованный уникальный `login`, соль `salt`, `rounds`, `password_hash`, `recovery_hash`, счётчик `failures`, `blocked_until`, признак `active`. `sessions`: SHA-256 `token_hash`, внешний ключ `user_id`, время создания `created`, последнее использование `last_seen`. Пароль, recovery-код и сеансовый токен в открытом виде не сохраняются. Новый файл БД получает ограниченные POSIX-права, если ОС их поддерживает; размещение каталога и резервных копий также должно быть защищено.

## Регистрация и пароль

Логин принимается только как `str`, проходит `casefold()` и шаблон `[a-z][a-z0-9_]{2,31}`. Новый пароль нормализуется NFC; после нормализации длина должна быть 15–128 символов, размер UTF-8 не более 1024 байт. Пробелы не удаляются, регистр не меняется. Малый `WEAK`-список предназначен для учебного теста и не заменяет проверку скомпрометированных паролей.

Для нового пароля генерируются 16 случайных байт соли и PBKDF2-HMAC-SHA-256 с 600 000 итерациями и результатом 32 байта. Значение `rounds` хранится рядом с параметрами учётной записи. Пониженное число итераций можно передать только тестовому экземпляру; обычное значение класса — 600 000.

## Вход и блокировка

Вход проверяет пароль через `hmac.compare_digest`. Неизвестный логин проходит фиктивное вычисление KDF, однако это не устраняет все тайминговые различия. После пяти подряд неверных попыток следующая проверка блокируется на 60 секунд; и правильный пароль в этот промежуток не создаёт сеанс. Момент `now == blocked_until` уже считается окончанием блокировки. Успех обнуляет счётчик. Единый результат `None` не раскрывает причину отказа.

Счётчик привязан к логину: посторонний, знающий имя учётной записи, может вызвать временный отказ в доступности владельцу. Это ожидаемая демонстрация варианта 19, а не неожиданная уязвимость реализации. Предложенные меры будущей версии: нарастающая задержка, ограничения источника и общей частоты, анализ нескольких сигналов, уведомление владельца, challenge для подозрительных запросов и безопасная процедура восстановления доступности. Эти меры здесь не реализованы. Фиксированное окно 60 секунд не останавливает распределённый подбор.

## Сеансы

После успеха создаётся непрозрачный `token_urlsafe(32)` токен. SQLite хранит только SHA-256 от токена. Быстрый SHA-256 уместен для независимо созданного случайного высокоэнтропийного токена: пространство перебора велико. Для пользовательских паролей он не годится, поскольку пароль может иметь малую энтропию; для них используется дорогая KDF.

`resolve(token)` принимает только ожидаемый base64url-формат, ищет запись и проверяет активность учётной записи, абсолютный срок 3600 секунд и срок бездействия 900 секунд. Граница срока закрытая: при разнице времени, равной лимиту, сеанс истёк. Иначе `last_seen` обновляется, а возвращается подтверждённый серверный `user_id`. `logout()` удаляет строку сеанса на сервере. Удаление клиентской копии само по себе этого не делает.

## Восстановление

`register()` выдаёт одноразовый случайный recovery-код вызывающей стороне ровно один раз; код представлен только своим SHA-256 в БД. `reset_password(login, code, new_password)` сверяет его в транзакции `BEGIN IMMEDIATE`, формирует новую соль и KDF, заменяет проверочный recovery-хеш, сбрасывает счётчик и удаляет все сеансы. Новый сеанс автоматически не создаётся. Неуспешная проверка не меняет запись. Это учебная модель заранее сохранённого кода, не полноценная процедура проверки личности через подтверждённый канал.

## Связь с моделью безопасности

Подсистема уточняет ранее сформулированные SEC-1 и SEC-14; новые требования SEC-23/SEC-24 и сценарии AT-25–AT-27 связывают хранение учётных данных и исследование блокировки с тестами. Новый сценарий TH-16/RS-13 отражает доступность аккаунта. Реализация не подключает аутентификацию к операциям транспорта, не реализует сетевые лимиты, MFA, журналирование входов, управление учётными записями администратором и распределённую обработку.

## Проверяемые ограничения

Стандартный отказ и фиктивный KDF уменьшают раскрытие логина, но PBKDF2 для неизвестных логинов создаёт вычислительную нагрузку. Учетная блокировка позволяет отказ в обслуживании. SQLite имеет файловую модель доступа одного узла. Recovery-код может быть украден до использования. Контроль структуры данных снижает последствия повреждения файла, но не защищает от полного контроля над файловой системой или процессом.
