# Авторизация заявок v0.8

## Границы модели

`AuthService` v0.7 отвечает за проверку пароля, выдачу и отзыв сеанса. `AccessService` (`app/authorization.py`) использует `AuthService.resolve(token)` как адаптер `resolve_session(token) -> int | None`: клиентский `user_id` не принимается. После подтверждения сессии сервис читает актуальные `active`, `role` и `department_id` из SQLite при каждом обращении.

Эта RBAC-модель относится к заявкам из ЛР5–6. Существующая модель поездок (`driver`, `dispatcher`, `manager`, `security_admin`) в `app/security/access_control.py` остаётся отдельной и не переименовывается. В текущем проекте нет сетевого API: `AccessService` — защищённый прикладной интерфейс и демонстрация его использования, а не доказательство защиты отсутствующего веб-развёртывания.

## Матрица прав

| Операция | user | operator | admin | specialist |
|---|---|---|---|---|
| `request.create` | Да | Нет | Нет | Нет |
| `request.read` | Только своя заявка | Все заявки учебной БД | Нет | Нет |
| `request.close` | Нет | Только `new → closed` | Нет | Нет |
| `role.assign` | Нет | Нет | Назначить `user`, `operator` или `specialist` другому обычному пользователю | Нет |
| `request.reopen` | Нет | Нет | Нет | Только `closed → new` в своём подразделении |
| Назначить `admin` / менять admin | Нет | Нет | Нет | Нет |
| Неизвестная операция или роль | Запрет | Запрет | Запрет | Запрет |

Роли не наследуются. Доступ к отдельным объектам проверяется после функционального разрешения: для `user` сервер сравнивает `requests.owner_id` с подтверждённым `users.id`. Для `operator` чтение ограничено общей учебной БД. `admin` имеет только разрешение управления ролями и не получает чтения заявок автоматически.

## Общая SQLite-схема и миграция

В репозитории нет сохранённой пользовательской SQLite-БД (файлы БД исключены из Git). Модуль v0.7 и репозиторий v0.6 принимали независимые пути. Для единой транзакции авторизации и операции v0.8 инициализируются на одном выбранном файле:

```python
auth = AuthService(database)
AccessService.initialize(database)  # идемпотентно вызывает обе миграции
access = AccessService(database, auth.resolve)
```

Миграция добавляет недостающие поля, не удаляет таблицы и столбцы:

- `users.role` добавляется с `DEFAULT 'user'`; `users.department_id` остаётся `NULL`, пока его не назначит доверенная подготовка;
- `requests.owner_id` и `requests.department_id` остаются `NULL` у старых записей;
- существующим заявкам назначается метка состояния `legacy`, а не выдумывается владелец или отдел;
- прежние хеши, соли, стоимость PBKDF2, recovery-хеши, сеансы и поля обращений (включая `description`, `category`, `priority`, `attachment_key`, `file_id`) сохраняются;
- только `AccessService.create_request()` создаёт защищённую новую заявку со статусом `new`, владельцем из подтверждённого ID и подразделением из серверной записи пользователя. Низкоуровневый `RequestRepository.add()` сохраняет запись со статусом `legacy`, потому что сам репозиторий не подтверждает пользователя и не назначает владельца.

Повторный вызов `AccessService.initialize(path)` проверен. Если у владельца проекта существуют две отдельные непустые БД из предыдущих запусков, данный код не объединяет их автоматически: сначала требуется резервное копирование и отдельная контролируемая миграция в общую БД. В текущем checkout таких файлов не обнаружено. Во время работы AccessService обе схемы находятся в одном файле, поэтому проверка текущей роли и изменение заявки используют одну транзакцию SQLite.

## Транзакция и отказы

Сеанс проверяется до транзакции доступа, так как `AuthService.resolve()` обновляет `sessions.last_seen`. Затем сервис начинает `BEGIN IMMEDIATE`, загружает актуальную роль и активность, проверяет разрешение, проверяет объект и выполняет запрос на том же соединении. Исключение вызывает `ROLLBACK` и передаётся вызывающему слою. Запрещённая операция не меняет роли и заявки. Обновление `last_seen` при отказе — отдельное служебное состояние сеанса.

Закрытие выполняется условным `UPDATE ... WHERE status='new'`; повторный/неподходящий переход отклоняется. Вариант 19 проверяет текущую роль, наличие отдела специалиста, закрытый статус и равенство серверных `department_id`, затем условно обновляет только `status`. Ни клиентский `owner_id`, ни `role`, ни `active`, ни `department_id` не входят в `ValidatedRequest`.

В открытой регистрации роль по умолчанию — `user`. Первоначальная учётная запись `admin` создаётся только доверенной локальной процедурой подготовки стенда; публичного метода назначения `admin` нет. Изменение обычной роли при действующем сеансе учитывается в следующем вызове, поскольку роль не кэшируется в токене.

## Требования и проверки

- SEC-25: подтверждение сеанса и загрузка актуальных полномочий для каждой операции.
- SEC-26: запрет чтения чужой заявки и одинаковый отказ для чужого/отсутствующего объекта.
- SEC-27: изменение роли только admin, без назначения/изменения admin; роль обновляется в следующем запросе.
- SEC-28: переходы `new → closed` и `closed → new` согласованы с проверкой роли и объекта в одной транзакции.
- SEC-29: вариант 19 требует `specialist`, совпадающий непустой отдел и `closed` статус.
- SEC-30: миграции повторяемы и сохраняют прежние записи и поля.

`tests/test_authorization.py` покрывает 20 базовых сценариев; `tests/test_variant19.py` — восемь проверок варианта; `tests/test_authorization_integration.py` содержит четыре проверки настоящей регистрации/входа/сеанса, миграции, валидации клиентских полей и сохранения вложения через `FileStore`. `demo_v08.py` работает только с временной БД и синтетическими данными.

## Остаточные ограничения и риски

Компрометация действующего токена позволяет действовать до его отзыва или истечения. Ошибочное назначение роли доверенным admin не предотвращается самой матрицей. Прямое использование низкоуровневого репозитория доверенным кодом в обход AccessService остаётся риском интеграции; сетевого интерфейса и полного контура эксплуатации нет. Неполные атрибуты legacy-заявок закрывают доступ специалисту, но требуют ручного предметного решения для назначения владельца/отдела.

`BEGIN IMMEDIATE` сериализует пишущие операции этой SQLite-БД, снижая параллелизм. Отзыв роли применяется к следующему обращению и не останавливает уже начатую транзакцию. Файловое хранилище не является частью транзакции SQLite; при ошибке добавления вложения выполняется компенсационное удаление, а не распределённый atomic commit. Целостность БД и каталога остаётся доверительной границей. Модель поддерживает одну текущую роль, не предоставляет жизненный цикл согласования/аудита назначения ролей и не является общей ABAC-системой или промышленной распределённой инфраструктурой.

Модель ориентирована на deny-by-default и проверку конкретного объекта на сервере [1, 2]. Параметризация SQL остаётся отдельной мерой и сама по себе не даёт разрешения на объект [3].
