Разрабатываемая система предназначена для учёта транспортных средств организации. Система будет вести карточки транспортных средств, хранить сведения об их техническом состоянии и закреплении за водителями, а также поддерживать планирование и контроль поездок. К основным функциям относятся:

- регистрация, аутентификация пользователей и ролевое разграничение доступа;
- ведение реестра транспортных средств (государственный номер, модель, статус, технические данные);
- закрепление транспортных средств за водителями и регистрация поездок;
- поиск и фильтрация сведений о транспортных средствах и поездках;
- журналирование событий безопасности;
- формирование учётных отчётов.

Обрабатываемыми данными являются идентификационные данные и учётные записи пользователей, сведения о транспортных средствах, поездках и статусах, записи журнала аудита. К защищаемым активам относятся учётные записи пользователей, секретные ключи, прикладные данные, исходный код, журналы безопасности и база данных.

## 7. Листинги конфигурационного модуля и точки запуска

### 7.1. `app/config.py`

Файл реализует загрузку настроек из переменных окружения и их проверку; библиотека `python-dotenv` загружает пары ключ–значение из `.env` в окружение процесса [3].

```python
"""Загрузка и проверка конфигурации приложения."""

import os
from dataclasses import dataclass

from dotenv import load_dotenv


@dataclass(frozen=True)
class Settings:
    """Проверенные настройки приложения."""

    app_name: str
    app_env: str
    secret_key: str


def load_settings() -> Settings:
    """Загрузить настройки из переменных окружения и проверить их."""
    load_dotenv()

    app_name = os.getenv("APP_NAME", "Система учета транспортных средств").strip()
    app_env = os.getenv("APP_ENV", "development").strip().lower()
    secret_key = os.getenv("APP_SECRET_KEY", "")
    allowed_environments = {"development", "testing", "production"}

    if not app_name:
        raise RuntimeError("Название приложения не может быть пустым")
    if app_env not in allowed_environments:
        raise RuntimeError("Недопустимое значение APP_ENV")
    if len(secret_key) < 32:
        raise RuntimeError("APP_SECRET_KEY должен содержать не менее 32 символов")

    return Settings(
        app_name=app_name,
        app_env=app_env,
        secret_key=secret_key,
    )
```

### 7.2. `app/main.py`

Файл содержит точку запуска приложения.

```python
"""Точка запуска системы учета транспортных средств."""

from app.config import load_settings


def build_startup_message(app_name: str, app_env: str) -> str:
    """Сформировать сообщение без раскрытия конфиденциальных данных."""
    return f"{app_name}: приложение запущено в режиме {app_env}"


def main() -> None:
    """Запустить приложение."""
    settings = load_settings()
    print(build_startup_message(settings.app_name, settings.app_env))


if __name__ == "__main__":
    main()
```

Основные особенности реализации:

- секретный ключ загружается из переменной окружения и не имеет опасного значения по умолчанию;
- минимальная длина секрета (не менее 32 символов) проверяется при запуске;
- допустимые режимы работы (`development`, `testing`, `production`) заданы явно;
- объект настроек объявлен как `frozen`-датакласс, то есть его значения нельзя изменить после создания;
- программа не выводит секретный ключ на экран и не записывает его в журнал.

## 14. Анализ реализованных мер безопасности

- **Секреты не хранятся в исходном коде.** Секретный ключ загружается из переменной окружения через файл `.env`, а не прописывается в коде.
- **Файл `.env` исключён из Git.** Правила `.gitignore` и команда `git ls-files` подтверждают, что реальная конфигурация не попадает в репозиторий.
- **Проверка конфигурации при запуске.** Приложение проверяет название, режим работы и минимальную длину секретного ключа (не менее 32 символов).
- **Отсутствие опасных значений по умолчанию.** Если секрет не задан, используется пустая строка, и приложение корректно завершается.
- **Неизменяемость настроек.** Объект `Settings` объявлен как `frozen`-датакласс, что исключает случайное изменение параметров после загрузки.
- **Секреты не выводятся пользователю.** Стартовое сообщение содержит только название приложения и режим работы.
- **Фиксация зависимостей.** Перечень библиотек зафиксирован в `requirements.txt`, что обеспечивает воспроизводимость окружения.
- **Изоляция окружения.** Виртуальное окружение `.venv` не входит в репозиторий и может быть восстановлено из `requirements.txt`.

Публикация секретного ключа в открытый репозиторий могла бы привести к его компрометации и использованию злоумышленниками для подделки данных или доступа к системам, поэтому вопросу исключения конфиденциальных данных из репозитория в работе уделялось особое внимание.

## 15. Ответы на контрольные вопросы

1. **Что включает в себя среда разработки программного обеспечения?**
   Среда разработки включает интерпретатор языка программирования, редактор исходного кода (IDE), систему контроля версий, менеджер зависимостей, средства тестирования и статического анализа, конфигурационные файлы и документацию проекта.

2. **Для чего применяется система контроля версий Git?**
   Git позволяет сохранять историю изменений, сравнивать версии файлов, фиксировать законченные этапы разработки, возвращаться к предыдущим версиям, организовывать совместную работу, а также определять автора и время каждого изменения [1].

3. **Чем рабочая директория отличается от индекса и репозитория?**
   Рабочая директория — это текущие файлы проекта, с которыми работает разработчик. Индекс — область, в которую файлы помещаются перед фиксацией (подготовленные к коммиту файлы). Репозиторий — хранилище истории сохранённых изменений (коммитов).

4. **Для чего создаётся виртуальное окружение Python?**
   Виртуальное окружение изолирует зависимости проекта от других проектов и системных пакетов, что предотвращает конфликты версий библиотек, обеспечивает воспроизводимость окружения и упрощает развёртывание [2].

5. **Почему каталог `.venv` не следует добавлять в репозиторий?**
   Каталог виртуального окружения содержит большое количество служебных файлов, не относящихся к коду проекта, и может быть восстановлен из списка зависимостей `requirements.txt`.

6. **Какие сведения относятся к секретам программного проекта?**
   К секретам относятся пароли, токены доступа, ключи API, криптографические ключи, строки подключения к базам данных, учётные данные администраторов и закрытые сертификаты.

7. **Почему пароли и ключи нельзя хранить непосредственно в исходном коде?**
   Исходный код обычно попадает в Git-репозиторий и может быть опубликован или просмотрен другими людьми. Это приводит к утечке конфиденциальных данных и компрометации системы.

8. **Чем `.env` отличается от `.env.example`?**
   Файл `.env` содержит реальные значения настроек, включая секреты, и хранится только локально. Файл `.env.example` содержит названия переменных и безопасные примеры заполнения и включается в репозиторий.

9. **Для чего используется файл `.gitignore`?**
   `.gitignore` задаёт перечень файлов и каталогов, исключаемых из репозитория: виртуальные окружения, конфиденциальную конфигурацию, служебные и системные файлы.

10. **Почему секретные параметры необходимо проверять при запуске?**
    Проверка позволяет своевременно обнаружить отсутствующие или некорректные настройки и не допустить запуск приложения с небезопасной конфигурацией, например с коротким или неустановленным секретным ключом.

11. **Для чего фиксируются версии программных зависимостей?**
    Фиксация версий в `requirements.txt` обеспечивает воспроизводимость окружения: на любой машине будут установлены одинаковые версии библиотек, что исключает ошибки, связанные с несовместимостью версий.

12. **Что представляет собой Git-коммит?**
    Коммит — это зафиксированное состояние проекта в определённый момент времени. Он сохраняет снимок изменений, автора, дату и сообщение о внесённых изменениях.

13. **Для чего используется метка v0.1?**
    Метка (тег) `v0.1` отмечает в истории Git конкретную версию проекта — начальную безопасную структуру. В дальнейшем по метке можно будет вернуться к данной версии.

14. **Какие файлы первоначальной версии проекта могут быть опубликованы?**
    Опубликованы могут быть файлы исходного кода, документация, шаблон конфигурации `.env.example`, список зависимостей и правила `.gitignore`. Не подлежат публикации файл `.env` и виртуальное окружение.

15. **Какие последствия может вызвать случайная публикация секретного ключа?**
    Публикация ключа может позволить злоумышленникам подделывать данные, получать несанкционированный доступ к системам и сервисам, что приведёт к нарушению конфиденциальности, целостности и доступности информации.
